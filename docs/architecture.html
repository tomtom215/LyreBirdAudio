Design Philosophy

Why Bash?

Bash is pre-installed on virtually every Linux system. Choosing Bash means: no pip/npm/gem conflicts, no build processes, no containers. Deployment is: git clone, run. The scripts check for Bash 4.0 or newer (the diagnostics for 4.4); the project's tests run on Bash 5.2 only.

Why Not Docker?

USB device management requires host-level udev rule creation and direct USB subsystem access. Containers add complexity that conflicts with physical USB port mapping, which is a core feature. LyreBirdAudio is designed for dedicated hosts where systemd services provide the process supervision.

Single-Responsibility Principle

Each script has one domain:

  • Orchestrator: user interface and delegation; it runs the other scripts and reports their results, and holds no streaming logic
  • Stream Manager: MediaMTX and FFmpeg process management, stream health, the status document
  • USB Mapper: device persistence via udev
  • Capability Checker: hardware capability detection and device configuration
  • Updater: version management
  • Diagnostics: system health checks
  • Installer: MediaMTX install, update and removal

The shared library (lyrebird-common.sh) holds what two scripts would otherwise copy: logging, the durable file writer and the MediaMTX configuration generator.

Process Ownership

The stream manager is the single owner of the MediaMTX it starts and of the FFmpeg wrappers it launches (the systemd unit mediamtx-audio.service). The standalone mediamtx.service stays supported for MediaMTX-only installs, but the two units conflict, and the manager refuses to start (exit 8) while another MediaMTX owns the node.

  • Processes are identified, not matched by name. The manager records each PID in its own PID file, and beside it, in <pid file>.id, the process start time (field 22 of /proc/<pid>/stat). A process is "ours" only while its start time still matches and its image is the expected one: for MediaMTX the configured binary run with the configuration file as its first argument; for a wrapper a Bash running that stream's generated script. A reused PID, another installation's MediaMTX, or an operator's ffmpeg reading a stream is never signalled.
  • Signals. stop sends SIGTERM to a wrapper's process group and every descendant, then SIGKILL after a timeout; force-stop sends SIGKILL at once. Both act only on recorded, verified processes. force-stop --kill-all --yes is the only broad kill; without --yes it prints what it would kill.
  • The installer follows the same rule. It stops MediaMTX through its owner (systemd or the stream manager), and otherwise only a process that runs the installed binary on the installed configuration. It never signals FFmpeg.
  • A repeated start changes nothing that works. When the recorded MediaMTX is alive and verified, only missing streams are started.

Locking

The scripts serialise on kernel flock locks, with one rule: a lock file is never deleted and never truncated.

  • The stream manager's lifecycle lock is /run/mediamtx-audio.lock; its configuration lock is /etc/mediamtx/.config.lock. start, stop, restart, reload and force-stop take the lifecycle lock; start/restart wait up to 30 s, stop/force-stop 5 s and then exit 5; the monitor takes it for its stream checks and skips its cycle if it is busy. The cron line's own /run/mediamtx-monitor.lock only keeps two monitor runs apart.
  • The kernel drops a flock when its holder exits, however it exits, so there is no stale lock and no lock-age or process-name guesswork. After the lock is won, the holder writes a record pid starttime into the file for humans: a failed acquire prints the holder from it (only if the start time still matches, so a recycled PID is never blamed) and the processes that have the file open.
  • Every long-lived child (MediaMTX, wrappers, their FFmpeg) is started with the lock descriptor closed, so a child cannot keep a lock after its parent is gone.
  • The updater (.git/lyrebird-updater/updater.lock) and the installer (/run/lock/mediamtx-installer.lock) have locks of their own.

Configuration Ownership

  • MediaMTX configuration. One generator (lyrebird_render_mediamtx_config in the shared library) serves the stream manager and the installer. A file whose first line is # Managed by LyreBirdAudio is ours and is rewritten, validated first, after a timestamped backup; any other file is the operator's and is never written. The rules are on Configuration.
  • Device configuration. audio-devices.conf is parsed as data by an allowlist parser: unknown keys, bad values and shell syntax are reported with file, line and key, and never executed. One parser serves validate, start, restart and monitor.
  • Generated wrapper scripts. Every value reaches a wrapper through printf %q, so a value is a quoted word and never code. The wrapper is checked with bash -n and installed by rename, so a running wrapper is never rewritten under its feet.
  • Durable writes. The MediaMTX configuration and the device configuration go through lyrebird_atomic_write: a temporary file in the same directory, fsync, rename, fsync of the directory. The stream manager's unit and cron files, the status document and the heartbeat are written to a temporary file and renamed, without fsync, so a reader never sees half a file. Whether a power cut leaves a file intact depends on the storage and was not tested.

Data Flow

Stream Startup Sequence

  1. start checks its settings, takes the lifecycle lock (exit 5 if another command holds it), and refuses (exit 8) if another MediaMTX owns the node
  2. If its own MediaMTX is already running, it keeps it and goes on to start only the streams that are missing. Otherwise it cleans up stale state and waits for the USB device list to settle
  3. It lists devices from /dev/snd/by-id/ (falling back to /proc/asound/cards) and skips any card with no capture PCM
  4. It checks that the three MediaMTX ports are free, renders the MediaMTX configuration if the file is managed, and launches MediaMTX; its PID is recorded before the wait for the API
  5. For each device it looks up the settings (friendly name, then full device name, then defaults), asks FFmpeg whether it can encode that channel count with that codec, generates the wrapper and launches it in its own session
  6. The wrapper supervises FFmpeg with exponential backoff
  7. MediaMTX's API confirms each path is ready; the result is judged against LYREBIRD_START_POLICY, written to /run/lyrebird/status.json, and returned as the exit status (0, or 9 after stopping what that run started)
  8. The cron job runs monitor every 5 minutes (see Monitoring)

Exponential Backoff Recovery

Each wrapper starts FFmpeg and, when it exits, waits before the next attempt. The wait starts at INITIAL_RESTART_DELAY (10 s) and is doubled before each wait, up to MAX_RESTART_DELAY (300 s), so with the defaults the waits are: 

After failure 1: wait 20s
After failure 2: wait 40s
After failure 3: wait 80s
After failure 4: wait 160s
After failure 5: wait 300s, then the wrapper exits

A run longer than WRAPPER_SUCCESS_DURATION (300s) resets the failure
counter, the restart counter and the delay.
The wrapper also exits after MAX_WRAPPER_RESTARTS (50) restarts without such a run,
or when its device is gone.

A wrapper that has exited stays down until the cron monitor starts it again (at most CRON_RESTART_MAX_PER_HOUR times per hour per stream). The wrapper itself sends no alert.

USB Device Persistence Flow

  1. USB device connected to a physical port
  2. Kernel registers sound card N (the number may vary between boots)
  3. udev rule matches the card: SUBSYSTEM=="sound", KERNEL=="card*", ATTRS{idVendor}=="XXXX", ATTRS{idProduct}=="YYYY", IMPORT{builtin}="path_id", ENV{ID_PATH}=="pci-0000:00:14.0-usb-0:2:1.0" — the card's physical position (controller + port), independent of USB bus and card numbering
  4. udev sets the ALSA card id: ATTR{id}="mic-left", so the card is hw:CARD=mic-left and appears as mic-left in /proc/asound/cards
  5. A second rule links /dev/sound/by-id/mic-left to controlC<N>
  6. On every boot or replug the same port gets the same name, regardless of enumeration order

Architecture Decision Records

Key technical decisions and their rationale:

ADR-001: Bash as Primary Language

Decision
Bash for all scripts (4.0 or newer is checked; tested on 5.2)
Rationale
Universal availability on Linux, no runtime to install, native system integration, easy to audit, familiar to sysadmins
Trade-offs
Limited to Linux/Unix; more verbose than Python for complex logic; requires careful quoting discipline

ADR-002: MediaMTX as RTSP Server

Decision
MediaMTX (formerly rtsp-simple-server) as the RTSP server
Rationale
Single binary deployment, low resource usage, REST API for health checks, active development
Trade-offs
External dependency; its API and configuration keys change between versions (the suite is tested against MediaMTX 1.15.0 to 1.21.3 and detects the API version)

ADR-003: FFmpeg for Audio Transcoding

Decision
FFmpeg as the audio capture and encoding pipeline
Rationale
Native ALSA support, codec flexibility, configurable for quality/performance trade-offs
Trade-offs
Must be installed; process lifecycle management complexity; some options are missing from older FFmpeg releases (the amix normalize option), which the manager detects by asking FFmpeg

ADR-004: Shared Library Pattern

Decision
lyrebird-common.sh sourced by the scripts
Rationale
One copy of logging, the durable writer and the MediaMTX configuration generator
Trade-offs
Must maintain backward compatibility; source order matters; the stream manager and the installer's install cannot run without it

ADR-005: Atomic, Durable File Operations

Decision
Write to a temporary file in the same directory, fsync, rename over the destination, fsync the directory (lyrebird_atomic_write)
Rationale
Prevents partial reads by concurrent processes; rename on one filesystem is atomic; the file survives a crash in either its old or its new form
Trade-offs
Slightly more complex code; a killed writer can leave a hidden temporary file, which nothing reads

ADR-006: udev for Device Persistence

Decision
udev rules name the sound card by its USB port position
Rationale
Kernel-integrated, no daemon required, survives reboots and reconnections
Trade-offs
Root required to install rules; moving a microphone to another port or changing hubs needs a new mapping; the mapper applies a mapping immediately, so no reboot is needed

ADR-007: Webhook-Based Alerting

Decision
Pure-Bash webhook support for Discord, Slack, ntfy, Pushover and generic endpoints, called by the operator
Rationale
Users choose their own notification platform; no email/SMS infrastructure required
Trade-offs
Requires network connectivity; rate limiting needed to prevent spam; no LyreBirdAudio component triggers it, so the operator decides what raises an alert

ADR-008: Prometheus Metrics Format

Decision
Export metrics in the Prometheus text exposition format
Rationale
Plain text (easy to debug), wide ecosystem (Grafana, Alertmanager)
Trade-offs
Metric names must stay stable; a source that cannot be read makes its metrics absent rather than 0

ADR-009: Kernel Locks That Are Never Deleted

Decision
flock on a stable path; the file is opened without truncation and never removed
Rationale
The kernel releases the lock when its holder dies, so there is nothing to clean up and no staleness test that can be wrong. Deleting a held lock file would give the next process a different lock
Trade-offs
A child that inherits the lock descriptor keeps the lock, so every long-lived child is started with it closed

ADR-010: Signal Handler Pattern

Decision
Scripts that start or change something install an EXIT trap and traps for the terminating signals (the stream manager: INT, TERM, QUIT, with the conventional 128+N exit status)
Rationale
Takes down what the run itself launched and removes its temporary files on every exit path
Trade-offs
More complex code; cleanup must be idempotent. A SIGHUP to an interactive stream manager run is a reload, not a restart
