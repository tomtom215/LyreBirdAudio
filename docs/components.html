ℹ️
What the suite does and does not run by itself

The stream manager's install command sets up a systemd unit and a cron job that runs monitor every 5 minutes. Nothing else is scheduled for you: the alert, metrics and storage scripts do their work only when you run them (from cron, a timer or your own scripts), and no LyreBirdAudio script sends an alert on its own.

🎛️ Orchestrator

lyrebird-orchestrator.sh is an interactive, menu-driven front end that runs the other scripts. It needs root and a terminal, and takes only -h/--help and -v/--version.

Usage

sudo ./lyrebird-orchestrator.sh

Main menu

OptionSubmenu
1) Quick Setup WizardFour steps: install MediaMTX, map USB devices, start streams, quick diagnostics
2) MediaMTX Installation & UpdatesInstall, update, reinstall (force), uninstall, installation status
3) USB Device ManagementMap devices, dry-run test, view mappings, detect capabilities, generate and validate the device configuration, remove mappings, reload udev rules
4) Audio Streaming ControlStart, stop, restart, status, stream URLs, monitor health
5) System DiagnosticsQuick, full, verbose, export a report
6) Version ManagementLaunch the updater, show component versions, show update history, roll back
7) Logs & StatusMediaMTX, orchestrator, stream manager and stream (FFmpeg) logs; quick health check

What it adds to the scripts it runs

  • It checks each delegated script against a SHA-256 baseline before running it, and logs to /var/log/lyrebird-orchestrator.log.
  • Start and Restart (menu 4, and the wizard's step 3) read the stream manager's status document after the command and report each stream: publishing, no bytes flowing, not publishing (with the manager's reason), or waiting for devices. Reading the document needs jq; without it only the exit status is shown.
  • A failed delegated script is reported with its exit status and what that status means (the tables below).
  • Version Management can show the updater's history and run --rollback.
⚠️
The wizard does not install the systemd unit or the monitor cron job

The wizard never runs the stream manager's install command. A node set up only through the wizard has no service that restarts the streams at boot and no monitor. Run sudo ./lyrebird-stream-manager.sh install afterwards (see Systemd Service).

📡 Stream Manager

lyrebird-stream-manager.sh detects USB microphones, starts MediaMTX and one FFmpeg wrapper per microphone, and reports which streams are actually publishing. It is the single owner of the MediaMTX process it starts: it only ever signals processes it recorded itself (PID file plus process start time), and refuses to start (exit 8) while another MediaMTX, such as mediamtx.service, owns the node.

Usage

# Individual streams (default): one RTSP path per microphone
sudo ./lyrebird-stream-manager.sh start

# Multiplex (mix all mics into one stream)
sudo ./lyrebird-stream-manager.sh -m multiplex -f amix start

# Multiplex (merge channels)
sudo ./lyrebird-stream-manager.sh -m multiplex -f amerge start

# Custom multiplex stream name
sudo ./lyrebird-stream-manager.sh -m multiplex -n studio start

# Machine-readable state, no root needed
./lyrebird-stream-manager.sh status --json

Commands

Commands (root is required except for status, config, validate and help)

restartStop, then start (running streams are interrupted; use reload to apply a MediaMTX configuration change without that)

status [--json]Show MediaMTX, each stream (path ready, bytes flowing, last error) and the overall state; --json prints the same as one JSON document. Exit 0 whatever the state
monitorOne health check; restarts what needs it (cron runs this every 5 minutes). See Monitoring

force-stop --kill-all [--yes]The only broad kill: every process that runs the configured MediaMTX binary or a file in the wrapper directory, with an FFmpeg logging there. Without --yes it prints the list and exits 1 without signalling anything

What start reports

A stream counts as started when MediaMTX's API reports its path as ready, not when FFmpeg is running. LYREBIRD_START_POLICY decides what start requires: degraded (default) needs at least one stream publishing, strict needs the stream of every detected microphone. A start that does not meet the policy exits 9 and stops what that run started; a stack that was already running is not touched. With no USB audio device at all, start brings MediaMTX up, reports waiting_for_devices and exits 0 (LYREBIRD_ALLOW_EMPTY_START=false makes it exit 6 instead); the monitor starts a stream for each device that appears later. A USB sound card with no capture PCM (a speaker or DAC) is skipped and does not count for the policy. The Configuration page lists both variables.

Features

  • One wrapper script per stream supervises FFmpeg and restarts it with exponential backoff (see Architecture)
  • Per-device settings in /etc/mediamtx/audio-devices.conf, read as data and never executed; validate checks the file
  • Locks are kernel flock locks on files that are never deleted, so a crashed run leaves no stale lock
  • MediaMTX configuration ownership: a file whose first line is # Managed by LyreBirdAudio is rewritten (after a timestamped backup) when its content changes; any other file is yours and is never rewritten (see Configuration)
  • Optional local recording: a ring of the last 12 five-minute segments per stream, in RAM by default (see Configuration)
  • One FFmpeg log per stream in /var/lib/mediamtx-ffmpeg/<stream>.log; the logs of the previous runs are kept as .log.prev.1, .prev.2, ...

🔌 USB Audio Mapper

usb-audio-mapper.sh creates persistent udev rules that give each USB audio device a fixed ALSA card name, tied to the USB port it is plugged into, so identical microphones keep their names across reboots whatever the enumeration order. It runs on Linux only and needs Bash 4.0 or newer.

Usage

# List USB sound cards, their ports and existing mappings (no root needed)
./usb-audio-mapper.sh --list

# Interactive mode (guided wizard)
sudo ./usb-audio-mapper.sh

# Non-interactive: name ALSA card 1 (vendor, product and port read from it)
sudo ./usb-audio-mapper.sh -n --card 1 -f mic-left

# Non-interactive by vendor/product id, choosing the port
sudo ./usb-audio-mapper.sh -n -v XXXX -p YYYY -u 1-2 -f mic-right

# Remove a mapping / preview rules without writing
sudo ./usb-audio-mapper.sh --remove mic-left
./usb-audio-mapper.sh -n --card 1 -f mic-left --dry-run

Options

FlagDescription
-i, --interactiveRun in interactive mode (default)
-n, --non-interactiveSkip all prompts
-c, --card <N>ALSA card number of a connected USB device
-v, --vendor <id>4-digit hex vendor ID
-p, --product <id>4-digit hex product ID
-u, --usb-port <port>Physical port, e.g. 1-2 or 1-2.3 (see --list)
--any-portMatch the device on any port (only safe with one device of that vendor/product id)
-f, --friendly <name>Name: lowercase letters, digits, hyphens; starts with a letter; at most 15 characters
-d, --device <text>Description stored in the rule comment (optional)
-l, --listList USB sound cards, ports and mappings
-t, --testList every USB device with its port (no changes)
-r, --remove <name>Remove a mapping
--dry-run / --no-applyPrint the rules only / write the rules without triggering udev
--rules-file <path>Rules file (default /etc/udev/rules.d/99-usb-soundcards.rules)
-D, --debugEnable debug output
-V, --versionPrint the version

Output

  • /etc/udev/rules.d/99-usb-soundcards.rules: the udev rules
  • The ALSA card id (shown in /proc/asound/cards, usable as hw:CARD=<name>)
  • /dev/sound/by-id/<name>: symlink to the card's control device

Exit Codes

CodeMeaning
0Success
1Error
2Usage error
3Permission (not root)
4Missing dependency (or not Linux, or Bash older than 4.0)
5Device not found or ambiguous
6Rule written, but the kernel did not apply the name
ℹ️
No Reboot Needed

Since v4.0.0 the mapper applies each mapping immediately and reads the card name back from the kernel to confirm it; it exits with status 6 and an explanation if the name did not take effect. Mappings written by v1.2.1 and earlier renamed no device; re-run the mapper once per device to replace them.

🎙️ Capability Checker

lyrebird-mic-check.sh reads each USB sound card's capabilities from the ALSA proc filesystem (/proc/asound) without opening the device, so it does not interrupt a running stream. It can write /etc/mediamtx/audio-devices.conf from what it finds. The stream manager does not run it: nothing generates the device configuration unless you do (or the stream manager writes its commented template).

Usage

# List all detected devices
./lyrebird-mic-check.sh

# Show details for card number 0
./lyrebird-mic-check.sh 0

# Generate the configuration file (a backup is made first)
sudo ./lyrebird-mic-check.sh -g --quality=normal

# Validate the existing configuration against the hardware
sudo ./lyrebird-mic-check.sh -V

# JSON output for scripting
./lyrebird-mic-check.sh --format=json

# List and restore configuration backups
./lyrebird-mic-check.sh --list-backups
sudo ./lyrebird-mic-check.sh --restore

Options

OptionDescription
-g, --generate-configWrite /etc/mediamtx/audio-devices.conf (asks before overwriting)
-f, --forceWith -g: overwrite without asking (a backup is still made)
--no-backupWith -g: skip the backup (not recommended)
--quality=TIERlow, normal (default) or high; see Quality Tiers
-V, --validateCheck the existing configuration against the hardware
--format=FORMATtext (default) or json
--list-backups, --restore [TIMESTAMP]List the backups; restore one (interactively, or the one with that timestamp)
-q, --quietErrors and warnings only

There is no --dry-run and no --json option. Backups are written next to the configuration as audio-devices.conf.backup.<YYYYmmdd_HHMMSS> (mode 600).

What It Detects

  • Supported sample rates, channel counts and sample formats of each USB sound card
  • Whether a device is in use (read from the ALSA proc files; the device is not opened)
  • Known USB audio adapter chips, with a warning that the capabilities are the chip's
ℹ️
USB Audio Adapter Note

For USB adapters with 3.5mm inputs, detected capabilities reflect the USB chip, not the microphone plugged into the analog jack. Always verify audio quality after configuration by checking actual recordings.

Exit Codes

CodeMeaning
0Success
1General error (invalid arguments, no devices, no /proc/asound)
2Configuration error (validation failed, write error)

📦 MediaMTX Installer

install_mediamtx.sh downloads MediaMTX from its GitHub releases, verifies the download against the release's checksums.sha256, installs the binary atomically and writes a configuration file and a systemd unit. Run it from a checkout: it needs lyrebird-common.sh and config/mediamtx.service next to it (without the library install stops with exit 4).

Usage

# Install the latest release
sudo ./install_mediamtx.sh install

# Install a specific version
sudo ./install_mediamtx.sh -V v1.15.0 install

# Update: verified download, atomic replace, rollback on failure
sudo ./install_mediamtx.sh update

# Check the installation, verify its integrity
./install_mediamtx.sh status
sudo ./install_mediamtx.sh verify

# Uninstall
sudo ./install_mediamtx.sh uninstall

# Show what would happen
sudo ./install_mediamtx.sh --dry-run install

Options

OptionDescription
-V, --target-version <version>Install this MediaMTX version (e.g. v1.15.0)
-p, --prefix <dir>Installation prefix (default /usr/local)
-f, --forceSkip confirmations; skip the checksum check only when no checksum is available (a mismatch is always fatal); replace a configuration file that is not LyreBirdAudio's, after saving a backup
-n, --dry-runShow actions without executing
-q, --quiet, -v, --verboseSuppress non-error output / debug output
-c, --config <file>Read INSTALL_PREFIX, CONFIG_DIR, STATE_DIR, SERVICE_USER and SERVICE_GROUP from a KEY=value file
--no-serviceSkip the systemd unit
--no-configSkip the MediaMTX configuration file

Behaviour

  • Update downloads and verifies the new release first, and only then stops MediaMTX through its owner (systemd, or the stream manager). It installs the binary atomically and starts MediaMTX again; if the new binary does not run or the service does not come back, the previous binary is restored. MediaMTX's own --upgrade is not used because it replaces the executable without any checksum check.
  • A MediaMTX that nobody supervises (started by hand) is stopped and not started again: the installer prints the command to start it and exits 0.
  • Processes are stopped through systemd or the stream manager, or, as a last resort, only a process that runs the installed binary with the installed configuration, after SIGTERM and a bounded wait. The installer never signals FFmpeg and never selects a process by name.
  • The configuration it writes comes from the same generator as the stream manager's: first line # Managed by LyreBirdAudio, API and metrics on 127.0.0.1, only RTSP enabled otherwise. An existing file without that first line is yours and is left alone unless --force is given. See Configuration.
  • The systemd unit mediamtx.service is rendered from config/mediamtx.service. It conflicts with mediamtx-audio.service (the stream manager's unit), so only one of the two runs, and it has no ExecReload: MediaMTX picks up a changed configuration file by itself.
  • install creates a mediamtx system user (MEDIAMTX_USER) when it does not exist.
  • The installer picks the release file for the host's OS and CPU: it recognises Linux, macOS and FreeBSD on amd64, 386, arm64, armv7 and armv6. The test suite runs on Linux x86_64; the other targets, and the BSD and macOS code paths in particular, are not tested.

1General error (unknown option or command, could not take the lock, could not write a file)
2Not run as root
3Unsupported operating system or CPU

🔔 Webhook Alerts

lyrebird-alerts.sh sends webhook notifications with per-destination rate limiting, using curl. It is a command and a set of functions you call; no other LyreBirdAudio script calls it, so nothing alerts until you run it from your own cron job or script.

Usage

# Interactive setup wizard
./lyrebird-alerts.sh setup

# Send test alert
./lyrebird-alerts.sh test

# Send a custom alert
./lyrebird-alerts.sh send --level warning --title "Alert" --message "Something happened"

# Check configuration status
./lyrebird-alerts.sh status

# Show current config
./lyrebird-alerts.sh config

Supported Webhook Types

TypeConfig ValueNotes
DiscorddiscordEmbeds with color-coded severity
SlackslackIncoming webhook format
ntfy.shntfySelf-hostable push notifications
PushoverpushoverMobile push for iOS/Android
Generic HTTPgenericAny HTTP POST endpoint

Only the request format was tested, against a stand-in for curl; no real webhook service was contacted.

Configuration

/etc/lyrebird/alerts.conf holds KEY=value lines, read as data (never executed); only names starting with LYREBIRD_ are accepted.

# /etc/lyrebird/alerts.conf
LYREBIRD_ALERT_ENABLED=true
LYREBIRD_WEBHOOK_URL="https://discord.com/api/webhooks/..."
LYREBIRD_WEBHOOK_TYPE="discord"
LYREBIRD_ALERT_RATE_LIMIT=300    # seconds an identical alert is suppressed per destination
LYREBIRD_HOSTNAME="field-unit-1"
LYREBIRD_LOCATION="North Forest"

Rate Limiting and Exit Codes

An identical alert (same type and message text) is not sent again to a destination that already confirmed it (HTTP 2xx) within LYREBIRD_ALERT_RATE_LIMIT seconds (default 300). A destination that failed has no record and is retried by the next identical alert. Concurrent identical alerts are delivered once per destination. A message that differs in any character (“87%” and “88%”) is a different alert. LYREBIRD_ALERT_DEDUP_WINDOW (default 3600) only sets how long delivery state is kept on disk.

Exit code of sendMeaning
0Delivered: every destination that needed the alert received it
1General error (for example send without --message)
3Total failure: no destination has the alert, at least one failed
4Suppressed: every destination already has it within the rate-limit window (not an error)
5Partial failure: some destinations have it, at least one failed; the next identical alert retries only the failed ones

Pre-Built Alert Functions

Source the script from your own script. send_alert returns the statuses above, so under set -e call it as send_alert ... || rc=$?.

source ./lyrebird-alerts.sh

alert_stream_down "mic1" "FFmpeg process died"   # stream, reason
alert_stream_up "mic1"
alert_device_disconnect "USB_Mic_2"
alert_disk_warning "82%" "/"                     # usage, mount point
alert_mediamtx_down "API not answering"          # reason (optional)
alert_network_down "eth0"                        # interface

📊 Prometheus Metrics

lyrebird-metrics.sh prints metrics in the Prometheus text exposition format, to stdout, to a file, or over HTTP. Run it as root for a complete scrape: another user's processes cannot be inspected closely enough, and what cannot be read is left out of the document and its collector reported failed.

Usage

# One-time output (stdout)
./lyrebird-metrics.sh

# HTTP server for Prometheus, on 127.0.0.1:9100
./lyrebird-metrics.sh serve --port 9100

# The same on every interface (no authentication, no TLS)
./lyrebird-metrics.sh serve --port 9100 --bind 0.0.0.0

# Atomic file for node_exporter's textfile collector
./lyrebird-metrics.sh --file /var/lib/node_exporter/textfile_collector/lyrebird.prom

--serve [PORT] is the older spelling of serve --port PORT. There is no --streams-only or --system-only. See Monitoring for the metric names, limits of the server and alerting rules.

Exit Codes

CodeMeaning
0Every collector completed (the server: stopped by a signal)
1Command-line error
2Nothing could be delivered: --file could not publish (the previous file is kept), or the server cannot run (no usable netcat, port in use)
3The output was delivered, but at least one collector failed (lyrebird_scrape_success is 0)

💾 Storage Management

lyrebird-storage.sh deletes old recordings, logs and temporary files under a retention policy, and cleans up harder when the disk fills. It runs once per invocation; there is no loop and no --interval option, so schedule it from cron or a timer.

Usage

# Show storage status
./lyrebird-storage.sh status

# Standard cleanup (retention policy); --dry-run shows what would be deleted
sudo ./lyrebird-storage.sh cleanup
sudo ./lyrebird-storage.sh --dry-run cleanup

# Emergency cleanup (oldest recordings first)
sudo ./lyrebird-storage.sh emergency

# One disk check, cleaning up when a threshold is crossed
sudo ./lyrebird-storage.sh monitor

Options

OptionDescription
-n, --dry-runShow what would be deleted without deleting
-d, --debugDebug output
-q, --quietcleanup and monitor: only warnings, errors and one summary line per run (on stderr)
--oncemonitor: accepted for clarity; monitor always checks once

Configuration

Settings come from the environment, or from /etc/lyrebird/storage.conf when it exists (the environment wins). The file holds KEY=value lines, read as data, never executed; a line that is not accepted is reported and ignored, and the run exits 4. A file that anyone can write, or that belongs to another user than root, is not read. In the file, directories must be absolute and RECORDING_DIR/LOG_DIR are accepted as other names for LYREBIRD_RECORDING_DIR/LYREBIRD_LOG_DIR; as environment variables only the LYREBIRD_ names exist. 

# /etc/lyrebird/storage.conf
RECORDING_RETENTION_DAYS=30   # Keep recordings for 30 days
LOG_RETENTION_DAYS=7          # Keep logs for 7 days
DISK_WARNING_PERCENT=80       # Warn at 80% disk usage
DISK_CRITICAL_PERCENT=90      # Critical at 90% usage
DISK_EMERGENCY_PERCENT=95     # Emergency cleanup at 95%
LYREBIRD_RECORDING_DIR=/var/lib/mediamtx-ffmpeg/recordings
LYREBIRD_LOG_DIR=/var/log/lyrebird

The script never reads the stream manager's AUDIO_RECORDING_PATH. If you move the recording directory of the manager, set LYREBIRD_RECORDING_DIR (and, for the emergency clear of the RAM buffer, LYREBIRD_BUFFER_DIR, default /dev/shm/lyrebird-buffer) to the same place. Files count as recordings when they end in opus ogg aac adts m4a mp3 flac wav.

Automated Cleanup

# /etc/cron.d/lyrebird-storage
0 3 * * *    root /path/to/lyrebird-storage.sh cleanup --quiet >>/var/log/lyrebird-storage.log 2>&1
*/15 * * * * root /path/to/lyrebird-storage.sh monitor --once >>/var/log/lyrebird-storage.log 2>&1

monitor prints nothing while the disk is fine, so the second line does not fill the log.

Exit Codes

CodeMeaning
0Success
1Usage error (unknown option, no command, --quiet with status/emergency, --once with anything but monitor)
3Finished, but at least one deletion failed or a directory could not be listed
4Finished, but lines of the configuration file were ignored (3 wins when both apply)

🔄 Version Manager

lyrebird-updater.sh switches a git checkout between releases and branches. An update is a transaction: your local changes are stashed, the service is stopped and backed up, the checkout is switched and verified, and everything is rolled back if a step fails. It needs Git 2.0+, Bash 4.0+ and flock.

Usage

# Interactive menu
./lyrebird-updater.sh

# Current version, branch and sync status
./lyrebird-updater.sh --status

# Fetch and list available versions (needs the network)
./lyrebird-updater.sh --list

# Show past updates, rollbacks and unfinished updates (local, no network)
./lyrebird-updater.sh --history

# Go back to the version before the last update, or to a tag or commit already in the clone
./lyrebird-updater.sh --rollback
./lyrebird-updater.sh --rollback v1.3.0

# Run post-update migrations manually
sudo ./lyrebird-updater.sh --migrate

The menu offers: 1) the latest stable release (the newest tag), 2) the default branch, 3) a specific version or branch, 4) check for updates, 5) detailed status, 6) discard local changes and reset. A switch that fails is reported and the menu stays open; Q leaves with the status of the last switch or reset.

Exit Codes

CodeMeaning
0Success
1General error (a failed switch, an invalid version, an unknown option)
2Prerequisites not met (git, awk, sed, grep, tput or flock missing; git or Bash too old)
3Not a git repository
4Could not reach the remote (--list then shows cached data) or no remote configured
5Permission: the repository is not writable or is owned by root, or the state directory or lock file cannot be written
6The requested or previous version is not available in this clone (a rollback never uses the network)
7Locked: another updater held the lock longer than LYREBIRD_UPDATER_LOCK_WAIT (default 30 s)
8Unusable git state (merge or rebase in progress) or an unreadable update journal
9Cancelled: a prompt was declined, or the run was interrupted
10The switch is done, but your saved changes conflict with the new version and were not re-applied; they are in the git stash
11The automatic rollback could not restore everything; the message names the git checkout --force command to run
12Standard input ended at a menu prompt

📚 Shared Library

lyrebird-common.sh holds the utility functions the scripts share. Most scripts fall back to their own definitions when it is missing; the stream manager and the installer's install command require it, because it holds the MediaMTX configuration generator and the atomic file writer.
