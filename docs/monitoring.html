Health Checking

lyrebird-diagnostics.sh runs read-only checks in three modes. It looks at the node, not at your audio: to see whether streams are publishing, use lyrebird-stream-manager.sh status (below) or the metrics.

ModeCommandCheck groupsUse Case
Quick sudo ./lyrebird-diagnostics.sh quick 8 Pre-operation verification, the wizard's last step
Full (default) sudo ./lyrebird-diagnostics.sh full 25 After configuration changes, periodic review
Debug (alias verbose) sudo ./lyrebird-diagnostics.sh debug 24, with log analysis Troubleshooting, more output

Run it as root: without root, file permission, log and service checks can report false problems (the script says so when it starts).

The RTSP port it uses comes from MEDIAMTX_RTSP_PORT (default 8554), the variable the other scripts use; MEDIAMTX_PORT is the fallback when MEDIAMTX_RTSP_PORT is not set. The FFmpeg log directory it checks is MEDIAMTX_FFMPEG_DIR (default /var/lib/mediamtx-ffmpeg, where the manager writes those logs); FFMPEG_LOG_DIR overrides it. It finds the MediaMTX process by identity, the program at MEDIAMTX_BINARY running the configuration file, so a process that merely mentions that path or is called mediamtx is not taken for it.

The Cron Monitor

sudo ./lyrebird-stream-manager.sh install writes /etc/cron.d/mediamtx-monitor, which runs lyrebird-stream-manager.sh monitor every 5 minutes under flock. The cron line acts on the exit status: 2 restarts mediamtx-audio; any other non-zero status is only logged with logger. The wizard does not write this file. The file also carries the stream mode and, when they differ from the defaults, the ports, bind addresses and RTSP_AUTH_MODE the node was installed with (see Configuration), because the monitor starts a MediaMTX that has died by rendering its configuration again.

What One Run Does

  1. Resource checks. MediaMTX over the file-descriptor limit (1000) or the CPU limit (40 %), or more wrapper processes than PID files, is critical: the monitor exits 2. High disk use (80 / 95 %), system memory (80 / 95 %) and a failing gateway ping are logged and never cause a restart, because restarting frees no disk. Each run also writes the heartbeat file.
  2. Silence probe. For each stream that MediaMTX reports ready, the monitor reads AUDIO_LEVEL_SAMPLE_DURATION (3) seconds of it back over RTSP, at most every AUDIO_LEVEL_CHECK_INTERVAL (240) seconds, and measures the level. No ALSA device is opened. When the maximum level stays at or below AUDIO_SILENCE_THRESHOLD_DB (-60 dB) for AUDIO_SILENCE_WARN_DURATION (60) seconds, one DEAD MIC error is logged for that silence episode, and one Audio recovered line when sound returns. The log is the only signal: there is no metric and no alert for it. The -60 dB default was checked against digital silence and a test tone only, not against real microphones. If you have configured RTSP read authentication, the probe gets a 401 and logs a probe error on every run; it never counts that as silence.
  3. Stream checks, while holding the lifecycle lock (if a start, stop or restart is running the monitor logs that and exits 0 without touching anything). It starts the stream of a device that has appeared or whose wrapper died; restarts a stream whose path MediaMTX reports not ready for DEEP_HEALTH_MAX_STRIKES (3) runs in a row (an API that does not answer, or answers 401/403, never counts as a strike); in multiplex mode restarts the stream when the set of devices changed; and, when MediaMTX is gone while the node is meant to run (start was run and stop was not), starts it again.
  4. Status. It rewrites /run/lyrebird/status.json.

Restart Budget

Restarts are bounded: at most CRON_RESTART_MAX_PER_HOUR (6) per stream per rolling hour, and the same budget for MediaMTX itself. A restart is only charged when it is really attempted: a card that is detected but cannot be opened (ALSA reports it unavailable), or a playback-only card, does not use up the budget. When the budget is used up the monitor logs it and leaves the stream down until the hour rolls over.

What It Does Not Do

  • It sends no alerts: no LyreBirdAudio script calls lyrebird-alerts.sh (see Webhook Alerting).
  • It does not clean up storage; schedule lyrebird-storage.sh separately.
  • The heartbeat file (/run/mediamtx-audio.heartbeat) holds the Unix time of the last monitor run. It proves that the monitor ran, not that MediaMTX or any stream is up.
  • There is no software watchdog. The settings that once suggested one (HEARTBEAT_INTERVAL, HARDWARE_WATCHDOG_*, ENABLE_HARDWARE_WATCHDOG) are ignored. Recovery is Restart=always on the unit and this monitor. For a hardware watchdog use systemd's RuntimeWatchdogSec= in /etc/systemd/system.conf (with the driver your board needs) or a watchdog daemon; the project neither implements nor tests that.

The Status Document

start, stop, force-stop, monitor and status write /run/lyrebird/status.json (LYREBIRD_STATUS_FILE), atomically, mode 0644. It describes the node as of the last of those commands, and the monitor refreshes it every cycle, so use timestamp_epoch to judge freshness and treat a missing file as "unknown". status --json prints the same document, computed live. 

{
  "schema_version": 1,
  "timestamp": "2026-11-11T22:10:44Z",
  "timestamp_epoch": 1794435044,
  "command": "monitor",
  "overall": "degraded",
  "policy": "degraded",
  "stream_mode": "individual",
  "mediamtx": { "running": true, "pid": 1234 },
  "streams": [
    { "device": "usb-Blue_Yeti", "card": "3", "path": "mic-left",
      "configured": true, "process_alive": true, "path_ready": true,
      "bytes_flowing": true, "last_error": null },
    { "device": "usb-Mic2", "card": "4", "path": "mic-right",
      "configured": false, "process_alive": false, "path_ready": false,
      "bytes_flowing": false,
      "last_error": "no stream wrapper is running for this stream" }
  ]
}
FieldMeaning
overallok: every expected stream publishes. degraded: some do. failed: none does, or MediaMTX is down although the node is meant to run. waiting_for_devices: MediaMTX is up and no capture device is detected. stopped: down on purpose. It does not depend on the start policy
configured, process_alive, path_ready, bytes_flowingThe wrapper was launched; the wrapper is running and provably this manager's; MediaMTX's API reports the path ready; the path's inbound byte counter grew between two samples LYREBIRD_FLOW_SAMPLE_SECONDS (3) apart. Each is true, false or null (not known: the API did not answer)
last_errornull while the stream publishes with bytes flowing; otherwise a sentence for a human, from the command that wrote the file. Not an enumeration
skippedPresent, as true, only on a card with no capture PCM (a speaker or DAC). It is listed but is not a stream; ignore entries with skipped when counting
policy, stream_mode, commandThe start policy in force, individual or multiplex, and the command that wrote the file

The orchestrator reads this document after a start or restart. lyrebird-metrics.sh does not. A script of your own can decide on it: ./lyrebird-stream-manager.sh status --json | jq -e '.overall == "ok"' exits non-zero unless every expected stream publishes.

Scheduling

Recommended Schedule

The monitor is already scheduled by install; do not add a second job for it. Add the other recurring jobs yourself:

# /etc/cron.d/lyrebird-monitoring

# Full diagnostic daily at 6 AM
0 6 * * * root /path/to/lyrebird-diagnostics.sh full >> /var/log/lyrebird-daily-check.log 2>&1

# Storage cleanup daily at 3 AM (one summary line per run)
0 3 * * * root /path/to/lyrebird-storage.sh cleanup --quiet >>/var/log/lyrebird-storage.log 2>&1

# Disk check every 15 minutes (silent while the disk is fine)
*/15 * * * * root /path/to/lyrebird-storage.sh monitor --once >>/var/log/lyrebird-storage.log 2>&1

Log Rotation

sudo ./lyrebird-stream-manager.sh install writes /etc/logrotate.d/mediamtx (when logrotate is installed), which rotates the MediaMTX log, the manager log and the FFmpeg logs in /var/lib/mediamtx-ffmpeg. The file config/lyrebird-logrotate.conf covers the logs that file does not: /var/log/lyrebird/*.log (the alert log) and the orchestrator, updater, diagnostics and USB mapper logs. Copy it to /etc/logrotate.d/lyrebird if you want those rotated; it lists none of the logs of the first file, so each log has one owner (the tests check that the two files name no log in common; they do not run logrotate).

Prometheus Metrics

Export metrics for Grafana dashboards and alerting. Run the exporter as root for a complete scrape.

# HTTP server on 127.0.0.1:9100
./lyrebird-metrics.sh serve --port 9100

# Or a file for node_exporter's textfile collector, replaced atomically (cron, every minute)
* * * * * root /path/to/lyrebird-metrics.sh --file /var/lib/node_exporter/textfile_collector/lyrebird.prom

Do not redirect the output with > into the collector directory: a scrape can read a half-written file. --file writes a hidden temporary file and renames it, and keeps the previous file if anything fails.

The HTTP Server

  • It listens on 127.0.0.1 unless you pass --bind. It has no authentication and no TLS, so a Prometheus on another host needs --bind ADDR (or 0.0.0.0) and a firewall, and targets: ['field-unit-1:9100'] works only that way.
  • It serves GET / and GET /metrics, one connection at a time, and generates the metrics after the request arrives. It needs a netcat (OpenBSD nc, ncat, traditional or BusyBox).
  • It is made for one poller. A second client that connects while one is being served, or within milliseconds after it, can be reset and must retry. For several scrapers, or anything beyond loopback, use --file with the textfile collector.

Behaviour to Know

  • A source that cannot be read makes its metrics absent, not 0, and its collector 0 (exit status 3). So lyrebird_mediamtx_up == 0 does not fire for an unreadable state; lyrebird_scrape_success == 0 does.
  • As a non-root user the exporter sees another user's processes only partly: it reports the affected collectors failed. Run it as root.
  • All MediaMTX API requests of one scrape share LYREBIRD_API_TIMEOUT (5 seconds); keep it below Prometheus's scrape_timeout. A refused connection is final at once; the API being down does not delay the scrape.
  • There is no metric for silent microphones; see the silence probe above.

Suggested Alert Rules

  • lyrebird_scrape_success == 0: a collector failed or a source could not be read
  • lyrebird_mediamtx_up == 0, lyrebird_api_up == 0: MediaMTX or its API is down
  • lyrebird_stream_up == 0, or lyrebird_active_streams below the number you expect
  • lyrebird_heartbeat_healthy == 0: the cron monitor has not run for 15 minutes
  • lyrebird_disk_usage_percent > 80

Webhook Alerting

⚠️
Nothing sends an alert unless you wire it up

No LyreBirdAudio script (the monitor, the storage script, the diagnostics, the metrics exporter) calls lyrebird-alerts.sh. The script and its alert_* functions are there for your own cron jobs and scripts. Prometheus alert rules (above) are the other route.

Setup

# Interactive webhook setup
./lyrebird-alerts.sh setup

# Test your webhook
./lyrebird-alerts.sh test

An Example Alert You Can Schedule

Tell the webhook when the stream manager does not report ok (every 5 minutes, for instance):

#!/bin/bash
# /usr/local/bin/lyrebird-check-streams.sh
state=$(/path/to/lyrebird-stream-manager.sh status --json | jq -r .overall)
if [[ "$state" != "ok" ]]; then
    /path/to/lyrebird-alerts.sh send --level error --type streams \
        --title "Streams not ok" --message "overall state: $state" || true
fi

Rate Limiting

An identical alert (same type and message text) is not sent again to a destination that already confirmed it within LYREBIRD_ALERT_RATE_LIMIT seconds (default 300). The check is per destination: a destination that failed is retried by the next identical alert, and one that succeeded is not sent it again. The exit status says which case happened (0 delivered, 3 total failure, 4 suppressed, 5 partial failure; see Webhook Alerts). 

LYREBIRD_ALERT_RATE_LIMIT=300  # Seconds an identical alert is suppressed, per destination

Performance & Optimization

The project has not measured CPU or memory use per stream. Use lyrebird_mediamtx_memory_bytes and lyrebird_stream_memory_bytes{stream} on your own hardware.

Thread Queue Tuning

If FFmpeg logs buffer underruns with several streams, raise the thread queue per device in /etc/mediamtx/audio-devices.conf (the default is 8192), or for all devices with the DEFAULT_THREAD_QUEUE environment variable:

# /etc/mediamtx/audio-devices.conf
DEVICE_MIC_LEFT_THREAD_QUEUE=16384

System Tuning

File-descriptor limits are set by the unit (LimitNOFILE=65536 for the stream manager's service); /etc/security/limits.conf does not apply to systemd services. The manager's own warning and critical levels are MAX_FD_WARNING and MAX_FD_CRITICAL.

USB Power Management

General Linux advice that this project has not tested: a USB device that is suspended can stop delivering audio.

# Disable USB auto-suspend for one vendor's devices via a udev rule
echo 'ACTION=="add", SUBSYSTEM=="usb", ATTR{idVendor}=="YOUR_VID", ATTR{power/autosuspend}="-1"' \
  | sudo tee /etc/udev/rules.d/50-usb-power.rules

Raspberry Pi Optimization

⚠️
USB Bandwidth Limitations

A Raspberry Pi shares USB bandwidth across its ports. The project's advice is one or two microphones per board; the test suite has not been run on a Raspberry Pi.

# Generate low-quality settings (mono where the card offers it, lower bitrate)
sudo ./lyrebird-mic-check.sh -g --quality=low
