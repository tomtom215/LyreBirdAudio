Security

What a default node exposes, what that allows, and how to close it. The full recipes are in the Security Guide in the repository.

⚠️
A default node is open on the network

Anyone who can reach TCP port 8554 can listen to every microphone and publish streams. On a network where every device is trusted that may be acceptable. On any other network you need the firewall rule or the authentication mode below.

What a default node exposes

The configuration the stream manager and the installer generate opens exactly these sockets (checked on MediaMTX 1.15.0, 1.18.0, 1.19.0, 1.21.1, 1.21.2 and 1.21.3):

WhatAddressWho can use it
RTSP every interface, TCP 8554 Anyone who can connect: read every stream, publish to any path name made of letters, digits, _ and -
RTSP over UDP every interface, UDP 8000 and 8001 Same as RTSP
Control API 127.0.0.1, TCP 9997 Programs on this machine, no password. Other machines: connection refused
MediaMTX metrics 127.0.0.1, TCP 9998 Programs on this machine, no password. Other machines: connection refused

SRT, MoQ (MediaMTX 1.19.0 and later), RTMP, HLS and WebRTC are switched off in the generated file, and no option turns them on. MEDIAMTX_API_BIND and MEDIAMTX_METRICS_BIND change the API and metrics addresses (empty means every interface; MediaMTX still answers 401 to other machines). RTSP always listens on every interface.

Check what your node exposes

sudo ss -tulpn | grep mediamtx

The current configuration prints five sockets: 0.0.0.0:8554 (tcp), 127.0.0.1:9997 (tcp), 127.0.0.1:9998 (tcp), 0.0.0.0:8000 (udp) and 0.0.0.0:8001 (udp). Anything else, or 9997 or 9998 on 0.0.0.0, means the node runs a file written by an earlier release (see below).

What each kind of attacker can do on a default node

Observed on MediaMTX 1.15.0 and 1.21.3:

  • A machine on the network that can reach TCP 8554. It can listen to every stream and publish under any matching name. Publishing to a name that is in use makes MediaMTX disconnect the current publisher, so the manager's own FFmpeg is cut off. It cannot reach the API or metrics.
  • Any local account on the node. Everything above through 127.0.0.1, and the API without a password: it can list streams and change MediaMTX's configuration, including a path setting that makes MediaMTX run a command as its own user (root under mediamtx-audio.service, mediamtx under mediamtx.service). A command started by an unprivileged account ran as uid 0.
  • A publisher (any network client in the default mode, or a compromised process on the node). It controls the audio the node reads back: the monitor decodes every published stream with FFmpeg, as root, to measure its level (AUDIO_LEVEL_CHECK_ENABLED, default true). Whether a hostile stream can exploit FFmpeg was not tested.

Nodes set up by an earlier release

A configuration written by an earlier release keeps its exposed settings until it is replaced:

head -n 1 /etc/mediamtx/mediamtx.yml
grep -E '^(apiAddress|metricsAddress|srt|moq):' /etc/mediamtx/mediamtx.yml
First lineWritten byExposes
# Managed by LyreBirdAudiocurrent manager or installernothing beyond the table above
# MediaMTX Configuration - Audio Streamsan earlier stream managerAPI and metrics on every interface (still 401 to other machines)
a row of #, then # MediaMTX Configurationan earlier installerthe same, plus SRT and (1.19.0+) MoQ; paths: {} refuses every publisher
anything elseyouwhatever you wrote

Stream manager nodes: the first start that launches MediaMTX replaces the file after saving a .bak copy; a node that keeps running applies it without a restart of the manager's processes with:

sudo ./lyrebird-stream-manager.sh reload

Installer nodes (mediamtx.service): the installer never rewrites a file without the marker unless you pass --force. sudo ./install_mediamtx.sh --force install replaces it after saving mediamtx.yml.backup.<date>-<time>, and also reinstalls the MediaMTX binary (add -V vX.Y.Z to keep your version) and the unit. Or edit three lines by hand: apiAddress and metricsAddress to 127.0.0.1:<port>, add srt: no, and moq: no only on MediaMTX 1.19.0 or later.

Security Checklist

Minimal (home use)

  • ☐ Keep the system updated: sudo apt update && sudo apt upgrade
  • ☐ Do not forward port 8554 from the internet
  • ☐ Know that everyone on your network can listen and can cut a stream off by publishing to its name
  • ☐ Run the exposure check after every upgrade

Standard (remote access or an untrusted network)

  • ☐ Turn on RTSP authentication
  • ☐ Limit TCP 8554 to the networks that need it with a firewall
  • ☐ Keep the API and metrics on 127.0.0.1 (the default)
  • ☐ Give nobody an account you would not trust with root, or protect the API
  • ☐ Keep log rotation working (install writes /etc/logrotate.d/mediamtx)

Enhanced (field deployment)

  • ☐ All standard items above
  • ☐ Reach the node through a VPN instead of exposing port 8554
  • ☐ Enable TLS if passwords or audio cross a network you do not control and you have no VPN
  • ☐ Protect webhook URLs and password files
  • ☐ Plan for physical access
  • ☐ Schedule updates

RTSP Authentication

The default mode is open. Defining authInternalUsers replaces MediaMTX's built-in users, so every setup keeps a password-less user for this machine: the manager's publishers, health checks and the metrics exporter connect to localhost without credentials.

Quick way: RTSP_AUTH_MODE=local-only-publish

The stream manager renders a user any that only 127.0.0.1 and ::1 can use (no password; publish, read, playback, API, metrics) and one read-only user per line of /etc/mediamtx/rtsp-users.conf (RTSP_USERS_FILE). Everyone else gets 401. It needs:

  1. A users file with lines user:sha256:<hash>, the hash being the base64 of the raw SHA-256 digest of the password. A plaintext or malformed line stops the start without printing the line. The hash has no salt: use long random passwords. 
    printf '%s' 'the password' | openssl dgst -sha256 -binary | base64
  2. MEDIAMTX_HOST must be a loopback name (the default is localhost).
  3. The variable must reach every process that can start MediaMTX: the service and the cron monitor, which starts MediaMTX again when it has died. Neither the unit nor the cron file carries it: 
    sudo systemctl edit mediamtx-audio
#   add:  [Service]
#         Environment="RTSP_AUTH_MODE=local-only-publish"
sudo sed -i 's/^CRON=1$/&\nRTSP_AUTH_MODE=local-only-publish/' /etc/cron.d/mediamtx-monitor
sudo systemctl restart mediamtx-audio
⚠️
The cron file is rewritten by install

Without the variable in the cron file, the monitor renders an open configuration when it restarts MediaMTX, and the managed file silently loses its users: after kill -9 of MediaMTX the file had no authInternalUsers and anonymous remote publishing worked again. Repeat the sed command after every install, or use a file you own (below), which is never rewritten. Check with grep -c authInternalUsers /etc/mediamtx/mediamtx.yml (1 = users are in the file).

Who owns /etc/mediamtx/mediamtx.yml

  • With the first line # Managed by LyreBirdAudio the file is generated. The stream manager renders it at every start that launches MediaMTX and on reload; a changed rendering is saved as mediamtx.yml.<UTC time>.<nn>.bak first (newest five kept) and replaced atomically. An edit to a generated file is lost at the next start.
  • Without it the file is yours. It is used as it is, validated, never rewritten, with one warning per start.
  • To keep hand edits, delete the first line. sudo ./lyrebird-stream-manager.sh --regenerate-config restart hands the file back after a backup.
  • The installer follows the same rule: --force is the only way to replace a file without the line.

Option 1: your own authInternalUsers

Delete the first line, then add this before paths:. Replace every change_me: it is a public example value.

###############################################
# Authentication
###############################################

# Authentication method. Available values:
# - internal: use internal users
# - http: use an external HTTP server
# - jwt: use JWT tokens
authMethod: internal

# Internal users (used when authMethod is "internal")
authInternalUsers:
  # This machine: publishers, health checks, API. No password, loopback only.
  - user: any
    pass:
    ips: ['127.0.0.1', '::1']
    permissions:
      - action: publish
      - action: read
      - action: playback
      - action: api
      - action: metrics
      - action: pprof

  # Remote listener - can view every stream
  - user: listener
    pass: change_me
    permissions:
      - action: read
      - action: playback

  # Remote listener limited to two streams.
  # A path that starts with '~' is a regular expression; without it, the
  # value is a literal path name.
  - user: birdwatcher
    pass: change_me_too
    permissions:
      - action: read
        path: '~^(mic1|mic2)$'

Checked on all six MediaMTX versions: a local publisher needs no credentials; an anonymous remote reader or publisher gets 401; listener can read but not publish; birdwatcher is refused outside the regular expression.

Options 2 and 3: keep passwords out of the file

  • Never write pass: "${VAR}". MediaMTX does not expand it: the literal text becomes the password (verified).
  • Option 2, environment: MTX_AUTHINTERNALUSERS_1_PASS overrides the password of the second user in the list. It works on MediaMTX 1.18.0 and later; 1.15.0 ignores it. Set it in the unit (systemctl edit mediamtx-audio) and use a placeholder nobody can match (below). With change_me as the placeholder, a cron-driven restart (which does not see the unit's environment) silently made change_me the password; the unmatchable hash locks the account instead.
  • Option 3, hash: pass: sha256:<output of the command above>. Right password accepted, wrong one 401 (verified). Keep the file readable by root only.
  pass: sha256:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
🚨
Passwords are readable on plain RTSP

MediaMTX's default is basic authentication. A capture on the loopback interface showed Authorization: Basic bGlzdGVuZXI6bGlzdGVuZXJwdw== (base64 of listener:listenerpw) on plain RTSP; over RTSPS neither the header nor the password appeared. Use RTSPS or a VPN.

TLS (RTSPS)

RTSPS hides the password and the audio from someone who captures the traffic. It does not, with FFmpeg as the client, prove which server you reached: an rtsps:// read succeeded against a self-signed certificate, and against an address the certificate does not name, even with -tls_verify 1, -ca_file or -verifyhost (the same options work for https://). A VPN does both. The Security Guide has the certificate commands (with the subjectAltName current clients want).

The generator has no TLS option: delete the first line of mediamtx.yml and add:

###############################################
# RTSP server (with TLS)
###############################################

# Encryption mode: "no", "optional" or "strict"
#   no: TLS disabled
#   optional: clients can connect with or without TLS
#   strict: only TLS connections allowed
rtspEncryption: optional

# Path to server certificate (PEM format)
rtspServerCert: /etc/mediamtx/certs/server.crt

# Path to server private key (PEM format)
rtspServerKey: /etc/mediamtx/certs/server.key

Use optional, not strict. The manager's publishers connect to plain RTSP on localhost:8554; with strict MediaMTX closed TCP 8554 and UDP 8000/8001 and nothing could publish. optional adds RTSPS on TCP 8322. To accept only encrypted connections from the network, keep optional and block TCP 8554 for everything but this machine. The key must be readable by whoever runs MediaMTX: root under the stream manager, the mediamtx account under mediamtx.service (mode 600 owned by root made it stop with permission denied).

API Security

The API listens on 127.0.0.1 only, so other machines get a refused connection. Every program on the node can use it without a password, and the manager's readiness check, stream probes and the metrics exporter rely on that. Nothing in LyreBirdAudio needs the API from another machine.

If other people have accounts on the node, give the API a password. In a file you own:

authMethod: internal
authInternalUsers:
  # The stream manager's own publishers and readers: this machine, no password.
  - user: any
    pass:
    ips: ['127.0.0.1', '::1']
    permissions:
      - action: publish
      - action: read
      - action: playback
  # The control API and the metrics endpoint: this machine, with a password.
  # The hash below is a placeholder nobody can match: replace it with the output
  # of the command in Option 3 (as it stands, nobody can use this account).
  - user: operator
    pass: sha256:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
    ips: ['127.0.0.1', '::1']
    permissions:
      - action: api
      - action: metrics

Another local account then got 401 from the API, also when trying to add a path that runs a command; local publishing without credentials still worked. What it costs: start continues with one warning (the API requires credentials); the monitor's deep health check reports unknown and never restarts a stream on it; lyrebird-metrics.sh has no credential setting, so lyrebird_api_up reads 0. Any local account can still read and publish streams through 127.0.0.1.

Network Security

Do not bind RTSP to one interface

Setting rtspAddress: 192.168.1.100:8554 by hand also makes MediaMTX refuse connections to 127.0.0.1, where the manager's publishers and probes connect (observed: publishing through 127.0.0.1 was refused). Use a firewall to limit who can connect.

UFW

UFW accepts loopback traffic and drops other incoming connections by default (read from its shipped files; UFW was not run):

# Allow SSH (always do this first!)
sudo ufw allow ssh

# Allow RTSP only from the local network
sudo ufw allow from 192.168.1.0/24 to any port 8554 proto tcp

# The API and metrics listen on 127.0.0.1 only: no rule needed
sudo ufw enable
sudo ufw status verbose

iptables

Accept loopback first. Measured with a second host: the allow/drop pair alone refused the other host and the machine itself; with the loopback rule first the machine worked and a host outside the allowed network was dropped.

# The stream manager's publishers and probes connect to 127.0.0.1
sudo iptables -A INPUT -i lo -j ACCEPT

# Allow RTSP from the local network only
sudo iptables -A INPUT -p tcp --dport 8554 -s 192.168.1.0/24 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 8554 -j DROP

VPN (recommended for remote monitoring)

Instead of exposing RTSP, connect remote viewers through a VPN such as WireGuard. It covers authentication and encryption of the server and avoids certificate handling. (Not run for this page.)

Fail2Ban

MediaMTX logs failed logins to /var/log/mediamtx.out in a different form per version, so the filter has two patterns (checked with fail2ban-regex against the logs of all six versions: three wrong passwords, three matches each). The earlier filter, which looked for client=, matched nothing. The jail and the log formats are in the Security Guide.

[Definition]
failregex = ^\s*WAR \[RTSP\] \[conn <HOST>:\d+\] failed to authenticate: authentication failed$
            ^\s*INF \[RTSP\] \[conn <HOST>:\d+\] closed: authentication (?:error|failed: authentication failed)$
ignoreregex =

Metrics and Alerts

The metrics exporter. lyrebird-metrics.sh serve listens on 127.0.0.1:9100 by default (--port, --bind), has no authentication and no TLS, and serves one connection at a time: it is made for a poller. Checked: other machines were refused by default; with --bind 0.0.0.0 they got the metrics without credentials, and the script logged a warning. The document lists stream names, versions, memory and CPU, device counts and disk usage. For several scrapers or any exposure beyond the machine, use --file with node_exporter's textfile collector.

Alerts. lyrebird-alerts.sh is off until enabled (LYREBIRD_ALERT_ENABLED). Its settings are in /etc/lyrebird/alerts.conf, written with mode 0600 by lyrebird-alerts.sh config and read as data.

  • The webhook URL is a secret (as are the Pushover token and user key and an ntfy topic).
  • Local accounts can read it while an alert is sent: it is a curl command-line argument, and an unprivileged account read the URL, token and user key from /proc/<pid>/cmdline during delivery.
  • http:// URLs are accepted without a warning. Use https://.
  • The destination receives the message text, the alert type, the host name, the location and the time. The default ntfy server is the third party https://ntfy.sh.
  • An identical alert is not re-sent to a destination within LYREBIRD_ALERT_RATE_LIMIT seconds (default 300). Nothing is signed.

File System Security

Modes observed after a first start as root:

  • /etc/mediamtx/mediamtx.yml and its .bak copies: 0644, or 0640 when they hold password hashes (MediaMTX configuration)
  • /etc/mediamtx/audio-devices.conf: 0644 (device names and settings)
  • /etc/mediamtx/rtsp-users.conf: yours (password hashes)
  • /var/log/lyrebird-stream-manager.log and /var/log/mediamtx.out: 0644 (stream names, client IP addresses)
  • /run/lyrebird/status.json and /run/mediamtx-audio.pid: 0644 (process IDs, per-stream state)
  • /etc/lyrebird/alerts.conf: 0600 (webhook URLs and tokens), written by lyrebird-alerts.sh config
# The manager runs MediaMTX as root, so root-only is enough
sudo chmod 640 /etc/mediamtx/mediamtx.yml
sudo chmod 600 /etc/mediamtx/rtsp-users.conf
sudo chmod 640 /var/log/lyrebird-stream-manager.log /var/log/mediamtx.out
sudo chmod 750 /etc/mediamtx /var/log/lyrebird

The manager keeps the mode you give mediamtx.yml when it replaces it, and logrotate (copytruncate) keeps the mode of the logs. A standalone mediamtx.service runs MediaMTX as the mediamtx account: use sudo chown root:mediamtx on the files it must read.

Log rotation. install writes /etc/logrotate.d/mediamtx. Do not also install config/lyrebird-logrotate.conf unchanged: it lists the same logs, and logrotate 3.21.0 then reported duplicate log entry and skipped the file install wrote, so those logs were no longer rotated. Copy only the stanzas for the other scripts' logs.

Library Integrity Check

The stream manager can check lyrebird-common.sh before it uses it. Set the hash in the service's environment (systemctl edit mediamtx-audio):

sha256sum lyrebird-common.sh | cut -d' ' -f1
# Environment="LYREBIRD_COMMON_EXPECTED_HASH=<that value>"

Checked: a wrong value stopped the manager with exit 1, the right value ran it. Only the stream manager has this check, and the value must be updated with every update of the library. Run the script as ./lyrebird-stream-manager.sh (or an absolute path): started as bash lyrebird-stream-manager.sh from its own directory it does not find the library at all.

Field Deployment Recommendations

ℹ️
Wildlife Monitoring Context

These recommendations matter most for unattended stations: limited physical access, and a network you may not control.

  1. Use a VPN — Connect remote units through WireGuard or OpenVPN rather than exposing RTSP to the internet.
  2. Turn on authentication — RTSP_AUTH_MODE=local-only-publish, or a file you own, if a VPN is not available. Add TLS if passwords cross an untrusted network.
  3. Keep updated — sudo apt upgrade, ./lyrebird-updater.sh (a menu), and sudo ./install_mediamtx.sh update (checksum-verified). Which release the updater offers matters: see SECURITY.md.
  4. Review logs — Check /var/log/lyrebird-stream-manager.log and /var/log/mediamtx.out for failed logins and unexpected clients.
  5. Physical security — Secure the device against physical access. USB port tamper detection is not built in.
  6. Emergency wipe plan — Keep a plan for removing the configuration, hashes, certificates and alert settings if a unit is compromised. shred is unreliable on flash storage; full-disk encryption protects better. The Security Guide has a script.
  7. Check exposure after every update — sudo ss -tulpn | grep mediamtx.

What this page was checked against

The YAML on this page was loaded by real MediaMTX binaries (1.15.0, 1.18.0, 1.19.0, 1.21.1, 1.21.2, 1.21.3), and the claims about what a node exposes or refuses were observed on them with the real stream manager, installer and renderer in a private network namespace (a second address on the loopback interface stands in for a remote client). Not checked: real USB hardware, a real systemd manager (units were checked with systemd-analyze verify only), ARM boards, UFW, fail2ban as a service, WireGuard, certbot and VLC.
